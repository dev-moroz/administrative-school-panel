## Цель и формат работы

- Учебный проект: потренировать **React/Next.js** (формы, валидация, серверные данные/кэш, таблицы и фильтры, состояние, авторизация, роутинг) и **NestJS** (бэкенд для автора всегда был второстепенным — хочет разобраться основательно). Опыт — Vue/Nuxt, нужен именно стек, отличный от Vue.
- Цель практики: чтобы на собеседовании по React можно было вспомнить, как это было на деле.
- **Режим работы:** не вайбкодинг. Ключевые куски пишет Anatoly сам; Claude проектирует, раскладывает на задачи, объясняет, ревьюит и берёт на себя рутину и сложные места. Не писать за него всё подряд — объяснять, почему так.
- Язык общения: русский.

## Что за продукт

Админ-панель для школы английского (индивидуальные занятия). Админ всё настраивает; ученики видят свой остаток занятий и расписание.

## Принятые решения

**Стек** (предложен в Codex, Anatoly согласился): монорепо на pnpm workspaces.
- Frontend: Next.js (App Router) + TypeScript + Tailwind + shadcn/ui. **Решено 2026-10-17:** Next запускается как Node-сервер в режиме `output: 'standalone'` (лёгкий Docker-образ), не static export. Рендеринг: страницы по умолчанию статические (SSG-оболочки), данные тянутся на клиенте (TanStack Query); SSR не используем без нужды, в страницах не вызываем `cookies()`/`headers()`. Сервер Next нужен для middleware (редиректы неавторизованных) и rewrites `/api` → Nest.
- Backend: NestJS + TypeScript, отдельное REST API
- БД: PostgreSQL + Prisma
- Авторизация: email + пароль, JWT (access/refresh)
- i18n: **изменено 2026-10-20** — каркас next-intl (язык в cookie, без префиксов в URL) оставлен, но пока только английский; RU и переключатель языка отложены. Переводы Anatoly отдаёт ИИ.
- UI: дружелюбный (не строгий), готовая Tailwind-база. **Скин ещё не выбран** (см. «Осталось»).

**Разработка без Docker:** приложения (Nest, Next) запускаются напрямую (быстрый hot reload). Postgres и Mailpit поднимаются через `docker compose up -d` (`docker-compose.yml` в корне). Сами приложения в Docker в разработке не запускаются. Версия Postgres в dev = версия в проде.

**Развёртывание:** локальная разработка → упаковка в Docker (пробная сборка образов — один раз после этапа 1, чтобы не копить сюрпризы; учесть архитектуру сервера) → самый дешёвый сервер (≈1 ядро, 2 ГБ). Система должна быть лёгкой. Деплой после MVP.

**Роли и доступ**
- В MVP две роли: `admin` (может всё; он же менеджер и учитель) и `student`. Роль `manager` возможна, но пока неважна.
- `teacher` — на будущее, должна быть сильно ограниченной; **откладываем**, в MVP не делаем.
- Роли и права делаем **настраиваемыми, как в админке Strapi** (роль = набор разрешений), чтобы новую роль или право добавлять без переделки. Не хардкодить проверки по имени роли — проверять разрешения.
- Админ создаёт учётку в интерфейсе, вводит почту, **логин и пароль уходят на эту почту** (простая автоматизация, без самостоятельной регистрации).
- Личный кабинет ученика: одна страница только для чтения — остаток занятий и время предстоящих занятий.

**Занятия и баланс**
- Только индивидуальные занятия; групповые — потом.
- Занятие: дата/время, преподаватель, ученик, длительность, статус `запланировано | проведено | отменено | неявка`.
- Оплата → добавление N занятий на счёт ученика (вручную). Можно докупать, не дожидаясь конца прошлого пакета.
- `проведено` → списать 1; `отменено` → не списывать.
- `неявка` → списывать или нет — **выбирает учитель/админ галочкой** на конкретном занятии.
- Перенос занятия: старое отменяется, создаётся/переносится новое.
- **Заморозка:** в период заморозки запланированные занятия отменяются, баланс сохраняется.
- Ручная корректировка баланса — с обязательным комментарием (например, «компенсация за отмену»).
- Цена: фиксированная цена за одно занятие. Стоимость пакета = число занятий. Персональные цены — в будущем.

**Платежи**
- Хранить исходные сумму и валюту (EUR, USD, крипта и т.д.), без автоконвертации. Конвертацию и курсы — позже.
- Поля: ученик, сумма, валюта, дата, способ (наличные/карта/перевод/крипта), комментарий, подтверждение (скрин или ссылка — оба варианта), кто внёс запись.
- Платёж и начисление занятий — **отдельные записи** (`Payment` и `LedgerEntry`), но создаются одной формой и одной транзакцией: админ сразу указывает число начисляемых занятий.
- История платежей должна показывать все валюты.
- Подтверждение на старте — свободное: скрин или ссылка, или просто пометка админа «средства поступили, +N занятий». Скриншоты предпочтительнее загружать в приложение (локальное хранилище в dev).

**Баланс может уходить в минус** (занятие проведено до оплаты) — это штатный случай, показывается как долг.

**Безопасность ролей — приоритет:** запрет по умолчанию, проверка владельца данных, ответы только через DTO, тесты «роль × эндпоинт» (подробности — `PLAN.md`, раздел 4).

**Токены:** httpOnly-cookie. В JWT только идентификатор пользователя; **роль и разрешения не кладём в токен — всегда читаем из БД** (единственный источник правды) на каждом защищённом запросе. Фронту права отдаёт Nest (например, `/auth/me`) только для скрытия кнопок; настоящую проверку делает guard на бэке.

**Аудит:** закладывается сразу (не вторым этапом) — хотя бы для занятий, баланса и платежей: кто, когда и почему изменил.

**Поля ученика (подтверждены):** ФИО, контакты, уровень английского, комментарий менеджера, дата начала обучения, часовой пояс, Telegram/WhatsApp.

**Не делаем в MVP:** уведомления, самостоятельная регистрация, кабинет учителя, группы/курсы, автоконвертация валют, персональные цены.

## Архитектурные опоры (рекомендация Codex, принята по сути)

Не строить «на вырост», но заложить:
- отдельные `User`, `Student`, `Teacher` — у одного пользователя сейчас могут быть все полномочия, роли потом не придётся переделывать;
- занятие — отдельная сущность, а не счётчик;
- **баланс — не число, а журнал операций** (начислено +8, проведён урок −1, ручная корректировка +1); остаток считается из журнала; это же основа аудита;
- участники занятия — отдельная связь (сейчас один ученик, позже без ломки группа);
- платёж и начисление занятий — отдельные записи, но создаются в одной транзакции.

Календарь (**входит в MVP**, решено 2026-10-17): единственная библиотека, упомянутая в диалоге, — FullCalendar (отдельного диалога с другой рекомендацией нет: «ChatGPT» у Anatoly = этот самый Codex-диалог). В первой версии — просмотр и создание/редактирование занятия по клику, без drag&drop, повторяющихся расписаний и конфликтов часовых поясов (это существенно сложнее).
